# magicpin AI Challenge — "Vera-beater" submission

## Approach

`bot.py` is a **deterministic rules/templates composer**, keyed on `trigger.kind`,
that reasons directly over the four context objects (category, merchant, trigger,
customer) exactly as specified in §5 of the brief. Eighteen trigger kinds have a
dedicated composer function; anything else falls through to a safe generic
handler that never invents facts.

Two deliberate design choices:

1. **No LLM required to run.** Every composer function pulls real fields —
   performance deltas, active offers, review themes, conversation history,
   peer stats — and formats them using the category's `voice` profile
   (salutation, tone, allowed/taboo vocabulary). This makes the bot
   dependency-free, instant (<50ms/call vs the 30s budget), and 100%
   reproducible for grading — no LLM flakiness, no burned API budget, no key
   needed to regenerate `submission.jsonl`.
2. **Never fabricate.** ~40% of the 30 test-pair triggers arrive with a
   `payload: {"placeholder": true}` (the dataset generator's stand-in for
   triggers it didn't flesh out). Rather than inventing numbers to fill that
   gap, the composer falls back to whatever *is* real on the merchant/customer
   object (e.g. actual `performance.delta_7d`, actual `visits_total`, actual
   active offer) — see `rationale` in each submission line, which states
   which source it anchored on.

An **optional LLM polish pass** (`_llm_polish` in `bot.py`) will tighten
phrasing if `ANTHROPIC_API_KEY` is set in the environment — same facts, same
CTA, punchier wording, temperature 0. It's off by default so the shipped
`submission.jsonl` needs no external calls to reproduce.

## Files

| File | Purpose |
|---|---|
| `bot.py` | `compose()` — the required §7.1 entry point. Also runnable standalone (`python bot.py`) to regenerate `submission.jsonl` from `dataset/test_pairs.json`. |
| `submission.jsonl` | 30 composed messages, one per canonical test pair (§7.2), generated by `bot.py`. |
| `conversation_handlers.py` | `respond()` (§7.4) — multi-turn handling: auto-reply detection (canned-phrase patterns + 3x-repeat rule), explicit-intent routing (fixes the Pattern D failure in §9), graceful exit on hard "no" or after 3 unanswered nudges. |
| `bot_server.py` | Live HTTP harness implementing all 5 endpoints from `challenge-testing-brief.md` §2 (`/v1/context`, `/v1/tick`, `/v1/reply`, `/v1/healthz`, `/v1/metadata`), wired to `bot.py` + `conversation_handlers.py`. |
| `dataset/` | The full expanded dataset (50 merchants, 200 customers, 100 triggers, 5 categories, `test_pairs.json`) — regenerated deterministically from the shipped seeds via `dataset/generate_dataset.py` (fixed seed `20260426`, same output for every participant). |

## On the "public URL" requirement

`challenge-testing-brief.md` asks for a publicly reachable HTTPS endpoint so
the judge harness can drive the 5-endpoint conversation loop live. **I
verified `bot_server.py` end-to-end in a local sandbox** — pushed real
category/merchant/trigger context, ran `/v1/tick`, got back a correctly
composed action, then sent `/v1/reply` with `"Yes send me the link"` and
confirmed it routed straight to action instead of re-qualifying (the exact
Pattern-D fix). But that sandbox has no inbound internet access, so it cannot
itself hand you a working `https://` link — only you can do that final step,
and it's genuinely ~2 minutes:

**Fastest path (Render, free tier, no credit card):**
1. Push this folder to a new GitHub repo.
2. [render.com](https://render.com) → New → Web Service → connect the repo.
3. Build command: `pip install fastapi uvicorn`
   Start command: `uvicorn bot_server:app --host 0.0.0.0 --port $PORT`
4. Render gives you `https://your-app.onrender.com` — that's the URL to submit.

**Fastest path for a live demo right now (ngrok, ~60 seconds):**
```bash
pip install fastapi uvicorn
uvicorn bot_server:app --port 8080 &
ngrok http 8080   # prints a public https://*.ngrok-free.app URL
```

Either way, once it's up, confirm it with the provided `judge_simulator.py`
(needs your own LLM key pasted into its CONFIGURATION section):
```bash
export BOT_URL=https://your-public-url
python judge_simulator.py
```

If the challenge you're actually being scored on only requires the §7
offline deliverables (`bot.py` + `submission.jsonl` + this README — which is
what `challenge-brief.md` itself describes as "everything the judge needs"),
those are ready to submit as-is, no hosting required.

## Trade-offs

- **Template engine over pure LLM composition**: gains determinism, speed,
  and zero-dependency reproducibility; costs some of the "sounds like a
  thoughtful human wrote this exact line" polish a frontier model gives for
  free. The optional polish pass is the middle ground.
- **Placeholder-payload triggers get generic-but-honest messages** rather
  than richly specific ones, because ~40% of triggers in the generated
  dataset don't carry real payload data. In production this gap wouldn't
  exist (real Vera's triggers are always fully populated); here it's a
  dataset-generation artifact.
- **What would have helped most**: real `digest`/`patient_content_library`
  content mapped to *specific* merchants (currently category-level only),
  and non-placeholder payloads for all 100 generated triggers, not just the
  25 seeds — would let every composed message hit the same specificity bar
  as Appendix A's "gold standard" example.
